# 就活ポートフォリオ動画 構成案（Gravity Shooter）

## 1. 動画のコアメッセージ（面接官に伝えるべき最大の強み）
この作品を通して、以下の3点を企業（エンジニア面接官）に強烈にアピールします。

1. **圧倒的な最適化技術 (1万オブジェクトの60FPS描画)**: `VirtualEntity`や`ObjectPool`を用いた無駄のないメモリ管理と、CPU負荷をゼロに抑える描画アーキテクチャ。
2. **すべてを一人で組み上げた「個の力」と「フルスクラッチの基盤」**: 自作エンジン（IrufemiEngine）からエディタ（IrufemiEditor）まで、個人制作で全要件を賄い切った基礎力の高さ。
3. **他職種とゲームの手触りを意識した設計**: レール変更に強いデータ駆動設計と、物理破綻を防ぎつつ爽快感を生むアクション実装。

---

## 2. 動画構成案（想定尺：約2〜3分）

### 【フェーズ1】 冒頭の掴みと前提共有（約15秒）
*   **映像:** 最も派手なシーン（大量のガレキを引き寄せ、ボスの弾幕を掻き分けて一斉掃射するインゲーム映像）。
*   **テロップ:**
    *   作品名：Gravity Shooter（仮）
    *   開発環境：C++20 / DirectX12 / 自作エンジン (IrufemiEngine)
    *   開発体制：**完全個人制作（エンジン・エディタ・ゲームロジック全て）**
*   **狙い:** 「面白そうなゲームができている」という結果（Result）を見せつつ、「完全個人制作の自作エンジンで動いている」という技術的ハードルを提示し、評価のベースラインを上げます。

### 【フェーズ2】 爽快感を生む「手触り」の追求（約30秒）
*   **要件設定:** 『グラビティデイズ』のような「引き寄せて投げる」爽快感と、壁抜けバグのない移動の実現。
*   **映像:**
    *   スプライン軌道に沿って自機が進みつつ、オフセットで滑らかに回避（バンキング）する様子。
    *   マルチロックオン（サテライトUI）の操作感。
*   **技術アピール (課題と解決):**
    *   「ガレキの引き寄せに物理演算をそのまま使うと、地形に引っかかる問題（Gap）が発生」
    *   「解決策として、引き寄せ時は物理判定を切り、ローカル座標でのsin/cosアニメーションで軽量に”騙す”実装を採用し、手触りを優先」

### 【フェーズ3】 ★最重要アピール★ 最適化とメモリ管理の「設計力」（約45秒）
*   **要件設定:** 1万個のガレキが舞う空間で、60FPSの処理落ちしない環境を維持する。
*   **映像:**
    *   1万個のガレキを描画しながら60FPSに張り付いているストレステストの様子。
    *   **※自作の外部パフォーマンス監視ツール（Telemetry Monitor）を画面端に並べて表示し、リアルタイムにオブジェクト数や処理時間が更新されている様子を見せる（定量的成果）。**
    *   **※進捗報告PDFで使った「Virtual Entity」や「Object Pool」の概念図をテロップ横に添える。**
*   **技術アピール (先見性とアーキテクチャ設計):**
    *   「ゲームのFPSに一切の影響（オーバーヘッド）を与えずに計測するため、UDP通信による完全独立の外部監視ツール（C#/WPF）を自作」
    *   「1万個のオブジェクトによるCPUボトルネックを**事前に予測**し、初期から専用の基盤を設計」
    *   **「`VirtualEntity`で大量のガレキを『座標データ』として管理しUpdate処理をゼロ化。引き寄せた瞬間のみ`ObjectPool`から実体をPromote（昇格）させる設計」**
    *   「GPU側でもInstancingと保守的カリングを行い、CPU負荷を根絶」
*   **狙い:** 「重くなってから対処した」のではなく、「最初から破綻を見越して最適化アーキテクチャを設計できる（先見性とシステム設計力がある）」ことを証明します。

### 【フェーズ4】 チーム開発を想定したレベルデザイン設計（約30秒）
*   **要件設定:** レールのカーブを変更しても、敵やイベントの配置が壊れないマップ構造。
*   **映像:**
    *   **自作の `IrufemiEditor` (ImGui) 上でJSONデータや数値をいじる様子。**
    *   エディタの数値を書き換えると、ゲーム内で敵の出現位置やウェーブのタイミングが即座に変わる様子を画面分割などで実演。
*   **技術アピール:**
    *   「絶対座標（X,Y,Z）ではなく、レールからの距離（Distance）と相対オフセットによるタイムライン管理を採用」
    *   「プランナーがコードを見ずに調整できるデータ駆動（Data-Driven）設計」

### 【フェーズ5】 絵作り・演出と締め（約20秒）
*   **映像:** `IrufemiEditor` のInspectorから、PostProcess Volume（Color Grading, Bloom等）の数値をいじり、絵作りの変化をリアルタイムに見せる。
*   **テロップ:**
    *   動的PostProcess Frameworkの構築
    *   バンド・デシネ風マルチレイヤーアウトライン（深度/法線/輝度による合成）
*   **狙い:** ツール開発力（エディタ実装力）と、グラフィックスへのこだわりを提示して締めくくります。

## 3. 次のアクション（動画撮影に向けて）

動画の撮影を進めるにあたり、以下の素材（フッテージ）を録画していくことを推奨します。

1. **ストレステストと外部ツールの実演**: 1万個のガレキが処理落ちなしで動く映像の横に、**自作の `Telemetry Monitor` (外部WPFアプリ)** を並べてリアルタイム監視している様子を録画。さらにPDFの「Virtual Entityの概念図」を添えて、「なぜ軽く動くのか」を視覚的かつ定量的に証明するシーン。
2. **IrufemiEditorの操作風景**: 自作エディタでパラメータ（ポストプロセスや敵のスポーン距離など）を調整し、即座にゲーム画面に反映される様子を録画。これは「開発環境も一人で構築した」という強力なエビデンスになります。
3. **デバッグビュー**: Bounding Boxの表示など、内部の当たり判定（BVH）やカリングがどう動いているかが視覚的にわかる映像。
